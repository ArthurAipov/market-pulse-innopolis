# Промпт для генерации тестов

Нейтральный шаблон: подходит любому ИИ-ассистенту. Подставьте код класса и требования, остальное
оставьте как есть. Результат **всегда** проходит ревью по чек-листу ниже — сгенерированный тест
нельзя принимать на веру.

## Шаблон

````text
Ты — разработчик, который пишет модульные тесты на Java 25.

Стек: JUnit 5 (Jupiter), AssertJ для проверок, Mockito для замены внешних зависимостей,
WireMock 3 для HTTP. Другие библиотеки не используй.

Что тестируем (код класса целиком):
<<< вставить исходный код >>>

Требования к поведению (из описания задачи, а не из реализации):
<<< вставить требования >>>

Как проектировать тест-кейсы:
- классы эквивалентности и граничные значения для каждого входного параметра;
- отдельно — негативные сценарии (null, пустое значение, неизвестные данные, ошибки зависимостей);
- не придумывай поведение, которого нет в требованиях; если требование неясно — перечисли вопросы,
  а не угадывай.

Правила оформления:
- один тест — одна проверяемая идея; структура Arrange–Act–Assert (Given–When–Then);
- имя метода описывает поведение, а не метод («duplicateIsNotAddedTwice», а не «testAdd2»);
- повторяющиеся проверки сводим в @ParameterizedTest (@CsvSource / @ValueSource / @MethodSource);
- проверки только через AssertJ (assertThat..., assertThatThrownBy...), без assertTrue/assertEquals;
- тест детерминирован: без Thread.sleep, без текущего времени и случайных чисел;
- не мокай то, чем владеешь и что дёшево создать (доменные объекты, простые классы) — мокай только
  внешние зависимости; в моках проверяй взаимодействие, только если оно и есть смысл теста.

Формат ответа:
1. Таблица тест-кейсов: класс эквивалентности / граница, вход, ожидаемый результат.
2. Готовый тестовый класс, который компилируется и запускается.
3. Список того, что НЕ покрыто, и почему.
````

## Примеры заполнения

**Unit-тест `Watchlist`** — требования: тикеры нормализуются к верхнему регистру; повторное
добавление (в любом регистре) не создаёт дубликата и возвращает `false`; `contains` не зависит от
регистра; `tickers()` — неизменяемое представление с порядком добавления; `null` вместо тикера — ошибка.

**WireMock-тест `HttpClientTInvestApiClient`** — требования: любой статус кроме 200 и любое тело,
которое не разбирается как массив котировок, дают `TInvestApiException`; ответ, пришедший позже
таймаута запроса, — тоже `TInvestApiException`. Зависимость — HTTP-сервер: поднимаем WireMock на
динамическом порту, заглушки задаём из теста.

## Чек-лист ревью сгенерированного теста

1. **Компилируется и проходит.** Прогнать целиком, а не по диагонали.
2. **Тест может упасть.** Сломать код (инвертировать условие, поменять оператор) — тест должен стать
   красным. Если не краснеет, он ничего не проверяет.
3. **Нет тавтологий.** Ожидаемое значение не вычисляется тем же кодом, который тестируется.
4. **Границы на месте.** Есть значение «ровно на границе», а не только «явно меньше» и «явно больше».
5. **Ожидания взяты из требований.** Не «как сейчас работает», а «как должно работать»; расхождения
   — повод разобраться, а не подогнать тест.
6. **Детерминизм.** Нет sleep, случайных данных, зависимости от порядка запуска и внешних сервисов.
7. **Моки по делу.** Не замоканы доменные классы; `verify` есть, только если взаимодействие и есть
   предмет проверки.
8. **Читаемость.** Имя тест-метода объясняет поведение; один тест — одна идея; нет копипасты вместо
   параметризации.
9. **Список «не покрыто» честный.** Дописать то, что ИИ не заметил (например, пустая строка вместо
   тикера).
