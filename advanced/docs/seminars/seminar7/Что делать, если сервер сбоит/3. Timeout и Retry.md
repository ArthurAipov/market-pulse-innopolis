# 3. Timeout и Retry

## Timeout — не ждать вечно

| Где | Как |
|---|---|
| `HttpClient` | `HttpClient.newBuilder().connectTimeout(...)` и `HttpRequest.newBuilder().timeout(...)` |
| `CompletableFuture` (в т. ч. `Reactor`) | `future.orTimeout(5, TimeUnit.SECONDS)` — завершит исключением `TimeoutException` |
| Свой цикл событий | таймер, который закрывает «зависшие» каналы |

```java
void example(ReactorTInvestApiClient client) {
    List<Quote> quotes = client.fetchQuotesAsync()
            .orTimeout(5, TimeUnit.SECONDS)        // у Reactor собственного таймаута нет — ставим снаружи
            .join();
}
```

Две разные цифры: `connectTimeout` — сколько ждать установки соединения, `requestTimeout` —
сколько ждать ответ целиком. Сервер, который принимает соединение, но молчит, ловится только вторым.

## Retry — повторить при сбое

```java
<T> T withRetry(Supplier<T> call, int attempts) {
    for (int attempt = 1; ; attempt++) {
        try {
            return call.get();
        } catch (TInvestApiException e) {
            if (attempt == attempts) {
                throw e;                                        // попытки кончились
            }
            sleep(100L << attempt);                             // 200, 400, 800 мс... — пауза растёт
        }
    }
}
```

| Правило | Почему |
|---|---|
| Повторять только **идемпотентные** операции (`GET`, но не «купить ещё раз») | повтор неидемпотентной операции может выполнить её дважды |
| Пауза растёт (экспоненциально) и с небольшим случайным разбросом (`jitter`) | иначе сотни клиентов повторят запрос одновременно и добьют сервис |
| Ограничить число попыток | иначе повтор превращается в бесконечный цикл |
| Повторять **временные** сбои (таймаут, `503`), а не постоянные (`404`, битый JSON) | повтор постоянной ошибки бесполезен |
